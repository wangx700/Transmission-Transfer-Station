## 1 名词速查

| 名词 | 直白说 | 为什么和昇腾有关 |
|---|---|---|
| 前缀缓存 | 请求开头那一段如果和上次一样，可以直接复用上次算好的结果，不必重算 | 复用省算力也省时间；昇腾上缓存就是 `kv_pool/ascend_store` 那套池子 |
| 前缀稳定 | 每次请求只在**末尾追加**新内容，开头一字不改 | 开头一变，缓存全部作废——这是所有缓存收益的前提 |
| 命中率 | 有多少比例的请求，开头真的复用了上次的缓存 | 是我们衡量「上下文治理有没有把缓存搞坏」的唯一硬指标 |
| 稀疏注意力按「组」打分 | Step5 的注意力不是逐 token 打分，而是把 **8 个 token 打包成一组**，按组打分再挑组 | 所以「能复用的开头长度」天然是 8 的倍数 |
| `prefix_match_unit` | 就是上面这个「8」的可配置值 | 复用长度不是它的整数倍时，昇腾侧直接报错——宁可不复用，不可悄悄算错 |
| summary_cache（小抄） | 稀疏注意力给每组 token 记的分数小抄，和 KV 分开存放 | 压缩、重排、换布局都会让小抄和 KV 对不上，必须重建 |
| top-k / ids | 每次只挑分数最高的 k 组去读 KV，「ids」就是被挑中的组号 | 英伟达与昇腾必须挑到**完全相同**的组号，否则同一句话两个平台走的不是同一条路径 |
| 确定性 | 同样输入必须得到同样输出，不因线程数、批次大小、卡型而变 | RL 要把推理产生的轨迹拿回去训练，输出必须可复现 |
| batch 不变性 | 同一句话单独跑，和与别人的请求拼成一批跑，结果要一样 | 拼批是吞吐的来源，但一变就漂概率，直接污染奖励 |
| logprob | 模型给每个 token 的概率 | 训练侧与推理侧对同一 token 算出的概率要对得上，偏差要能度量 |
| MTP（投机解码） | 先一次猜多个 token 再回头校验，猜对的直接采纳 | 提速手段；开了之后要先证明「不改变结果」 |
| CLM | Step-Code 的自动压缩器：长会话时把旧内容压短，只在「下一次请求」里用压缩版 | 压缩改写开头 → 缓存失效，这是一笔隐性成本 |
| 口径 | 统计与判定所依据的标准 | 换口径结论就变，所以本文凡结论都标口径 |

## 2 主文档 1.2 那五个改动，人话版

上游 `step-5-preview-tracking` 分支在区间内只提交了一次（10-10，PR #30），做的是「让 Step5 在英伟达 H200 这类新卡上跑得动、跑得对」。拆成五件事：

1. **放开门禁**：原来只允许最新的 SM103 卡，现在把 SM90 也放进来。
   → 昇腾**不需要**搬这个判断（我们没有 SM 版本这回事），但要有等价物：启动时把该查的查清楚，不满足就退出。
2. **按卡挑实现**：SM90 走新写的打分核，其他卡继续用 FlashInfer。
   → 昇腾只有一条 aclnn 路径，不用二选一；要求只有一条——**换实现不能换结果**。
3. **新写一个打分核**：FP8 量化打包、并且规定「超出有效长度的区域当作看不见」。
   → 内核不移植（它是英伟达专用指令），但**这条规矩要移植**：越界区域永远不能被选中。
4. **把「选哪些组」定死**：强调不能出现「同分情况下顺序随机」。
   → 昇腾已有三道保险（环境变量默认开启 + 算子升序返回 + 追加组时不挤掉已选中的），但缺一个**跨平台对照证据**。
5. **补测试矩阵**：覆盖 k=2/7/512、分页边界、量化打包。
   → 把这三张表搬到昇腾侧重跑。

一句话：**上游在解决「英伟达新卡能不能跑对」，我们在解决「昇腾能不能得出同样的结果」。**

## 3 昇腾到底要做哪 4 件事，为什么

主文档说「要动 4 处 + 补 2 条验收」，翻成人话：

| 要做的事 | 为什么非做不可 | 做完的标志 |
|---|---|---|
| ① 重新量复用率 | 上游把压缩器设成默认开启（#232）。压缩会改写请求开头 → 原来能复用的缓存用不上了。不重新量，我们说的「命中率」就是旧数据 | 给出「开压缩 / 关压缩」两组的复用率与成本对比 |
| ② 让小抄和缓存对得上 | #255 把上下文预算和「用了哪个工具」写进了小抄的键。键变了，旧小抄就不能用了，混用就会算错 | 压缩前后各跑一次，验证键变化即重建、不混用 |
| ③ 验证时保证只在末尾追加 | #267 修的是「只追加新内容时，原提示不被挪动」。这正好是我们做缓存验证的前提 | 验证用例明确写成「只追加」，并断言开头不变 |
| ④ 开头长度必须是 8 的倍数 | #293 是硬约束：不是整数倍就直接报错（`prefix_match_unit` 校验） | 有一条用例覆盖「整除 / 非整除」，非整除时按预期报错 |

另外两条只是**补验收**，不是改内核：

- **#284**：长会话压缩中途失败要能重试，并报出还剩多少余量。
- **#296**：计划模式下工具块顺序保持不动（否则开头又变了）。

## 4 主文档 1.3 的七组，一句话各自在做什么

| 组 | 一句话 |
|---|---|
| A 上下文与压缩 | 管「长会话怎么变短」以及「变短之后缓存还能不能用」——唯一和昇腾有关系的组 |
| B 子 Agent 与 workflow | 管「多个 Agent 怎么分工、后台任务怎么回来」——调度层面的事 |
| C 工具链与技能 | 管「读写文件、搜索、跑命令、加载技能」这些本地动作 |
| D CLI/TUI 与会话 | 管「命令行怎么用、界面怎么显示、会话怎么存和搜」 |
| E 认证、渠道与权限 | 管「怎么登录、权限多大、接不接飞书」 |
| F 平台与安装更新 | 管「Windows 上怎么装、怎么升级」 |
| G Web 与仓库治理 | 管「网页端功能、文档、贡献流程」 |

判词的含义：**需要** = 已经打到我们的约束上，必须动手；**需评估** = 先加一个用例再看，多半只补测试；**不需要** = 只当背景，不产生工作量。54 个 PR 里只有 6 条落在前两档。

## 5 常见疑问

**问：为什么老强调「开头不要变」？**
答：因为缓存复用的是「开头」。开头一动，前面算的全部作废，等于把长会话的最贵那段重算一遍。压缩、插入提示、重排工具块，都可能动开头。

**问：CLM 默认开启，是不是就更省钱？**
答：不一定。要算三笔账：压缩那一次的调用成本 + 后续输入变短省下的钱 − 缓存失效多花的钱。默认值只是「至少省 1,024 token 且省 5% 才采纳」，不等于总体更便宜。

**问：为什么「组号一致」被排成最高优先级？**
答：因为它是 RL 能复现的**唯一**数值前提。同一句话两个平台选到不同的组，就是在读不同的 KV、走不同的路径，后面的概率必然不同，轨迹也就没法拿去训练。

**问：为什么昇腾要「启动即失败」？**
答：能力缺失如果拖到 rollout 中途才炸，训练侧看到的现象只是「这条轨迹没结果 / 奖励很低」，根本看不出是环境问题，排查成本极高。启动时报错能一句话说清缺什么。

**问：SM90 的结论为什么不能直接用在昇腾上？**
答：那是英伟达 Hopper 专用的稀疏注意力路径，昇腾走的是 aclnn 算子 + 自己的一套池子。上游「在 H200 上验证过了」不代表「昇腾也支持」。

**问：batch 不变性跟奖励有什么关系？**
答：推理侧拼批变了、概率跟着漂，同一条轨迹前后两次评估的分数就不一样，奖励信号自身带噪声，训练会被这种噪声带偏。
