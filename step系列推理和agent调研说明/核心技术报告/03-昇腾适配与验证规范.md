## 2. 依赖与接口链

`设备/driver/firmware → CANN/算子包 → torch/torch_npu → 配套vLLM core/Ascend → 模型loader/processor → 算子与缓存 → 服务协议`。

原核验的v0.23.0与v0.26.0rc1分别配套对应core release；相关公开配置使用CANN9.1.0、torch2.10.0、torch_npu2.10.0.post4及Triton Ascend3.2.2（按硬件范围）。这是环境记录，不是Step5认证配方。main须遵循所选Ascend commit的verified core文件。[依赖](https://github.com/vllm-project/vllm-ascend/blob/v0.23.0/requirements.txt)、[verified core](https://github.com/vllm-project/vllm-ascend/blob/c076a131097fdfac9db4b57c8cf55bfd45ea0ca5/.github/vllm-main-verified.commit)

复用3.5/3.7既有适配；若修改后端或新增精度/功能路径，需保持gate、路由bias/缩放、激活和MTP语义；Audio模型还需processor、encoder、codec或DiT/VAE。安装成功、HTTP健康检查或文本输出正常，不证明这些分支正确。[Step patch](https://github.com/vllm-project/vllm-ascend/blob/c076a131097fdfac9db4b57c8cf55bfd45ea0ca5/vllm_ascend/patch/worker/patch_step3p5.py)

## 3. 部署验收与研发验收分开

**已有支持部署：** 固定已支持版本/设备，做目标业务质量、长度/并发和服务SLO测试；满足要求即可进入使用，不强制重复底层适配验收。

**新增路径或改动后端：** 涉及MRV2、算子/缓存、量化或训练采样路径变化时，按下面顺序开展增量验收。音频/Step5未确认完整支持的路径也须先补齐前置资料。

1. 固定checkpoint、代码commit、软硬件、精度与并行配置，建立短文本BF16基线。
2. 比较参考输出、logprob及关键算子；MoE额外核对路由和权重混合语义。
3. 分别开启工具、多模态、MTP、量化、图模式和缓存特性，避免同时改变多项条件。
4. 扩展长度与并发，记录显存、错误率、吞吐与尾延迟；音频增加内容正确性、连续性和打断测试。
5. RL验证策略版本、logprob、样本过滤与有效采样收益；Agent验证工具副作用与完成证据。

## 4. 指标定义与比较约束

表注：以下是建议统一记录的指标定义，阈值由业务SLO和参考基线确定；单请求和聚合指标必须分开。

| 指标 | 本报告建议口径 | 常见误用 |
|---|---|---|
| TTFT | 请求进入服务至首个输出token，说明是否含网络/排队 | 仅计prefill kernel |
| TPOT | 输出阶段非首token平均间隔；另报尾部分布 | 用聚合tokens/s取倒数当单请求延迟 |
| 吞吐 | 测量窗口内有效输出token/墙钟时间 | 把峰值当持续容量 |
| 首音延迟 | 从约定输入终点到首段可播放音频 | 用首文本token或空泛占位语代替 |
| RTF | 处理耗时/音频时长，注明批量、并发及包含阶段 | 由RTF直接推导对话首音延迟 |
| 任务成功率 | 以测试、数据库或产物最终状态验收 | 使用模型自报完成 |
| 每成功任务成本 | 测量集全部尝试的总费用/成功任务数，列出重试与工具费 | 只计成功样本本身或只比token单价 |

压测报告至少包含输入/输出长度分布、到达率或并发、warmup、测量时长、错误处理、模型/框架版本和硬件。比较应保持任务与服务条件一致，并同时报告质量和成本，避免仅选择最有利的吞吐点。

## 5. 容量边界

激活参数决定部分计算路径，不免除其他专家权重的存储。600B参数按BF16粗算约1.2TB，尚不含KV、workspace、通信和副本；这是算术估计，不能作为卡数配置。API最大输入、最大输出仍受总上下文约束；Step5的1M/64K不能同时取满。量化格式必须匹配NPU算子，不能直接迁移NVIDIA专用格式。
