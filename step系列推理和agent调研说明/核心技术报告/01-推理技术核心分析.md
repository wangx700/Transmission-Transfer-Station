## 2. Attention：降低访存必须考虑计算代价

**MFA。** [论文] Step-3采用低秩query路径和共享K/V；其关注点是同时控制历史状态与attention计算，而不是只追求最小KV。[论文§2、§5](https://arxiv.org/html/2507.19427)

[工程分析] 性能下界可写为`T ≥ max(F/P_eff, D/BW_eff)`，F是运算量、D是实际读取字节，P_eff/BW_eff是有效算力/带宽。它忽略启动、通信和排队，不能当作完整时延。压缩KV若显著增加F，可能把瓶颈从带宽转移到计算。

**SWA与Gate。** 3.5/3.7通过局部/全局层混合控制访问范围；head输出乘sigmoid gate后再进入输出变换。窗口减少可见位置，gate调节结果注入；gate不自动跳过已完成的attention。全局层保留跨远距交互，也保留随长度增长的KV需求。[门控实现](https://huggingface.co/stepfun-ai/Step-3.7-Flash/blob/main/modeling_step3p7.py)

**Sparse GQA。** [媒体转述] Step5用索引选取相关历史信息并组织块级计算；局部Indexer/Top-k成本降至1/8，尚缺完整硬件与端到端消融。[技术报道](https://news.qq.com/rain/a/20260920A06EUP00)

[原理] Prefill先从多个输入位置产生Q/K/V，再执行attention；多个query的候选重叠时，融合调度可能复用片上K/V。K/V投影原本就不需为每个query重算。索引去重也不能减少此前已经发生的评分计算。普通decode每请求每轮通常只有一个新query，不能直接套用同一请求内的多query复用。H1等“历史块”只作示意，不代表Step5已确认的选择粒度或缓存页。

## 3. MoE与EP：激活量小不保证低时延

详细机制、接口流程、拖尾治理、主要参考仓库及昇腾工程投入判断见[MoE与EP专题](https://github.com/wangx700/Transmission-Transfer-Station/blob/main/step%E7%B3%BB%E5%88%97%E6%8E%A8%E7%90%86%E5%92%8Cagent%E8%B0%83%E7%A0%94%E8%AF%B4%E6%98%8E/%E6%A0%B8%E5%BF%83%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/05-MoE%E4%B8%8EEP%E6%9C%BA%E5%88%B6%E3%80%81%E6%8B%96%E5%B0%BE%E6%B2%BB%E7%90%86%E5%8F%8A%E6%98%87%E8%85%BE%E5%B7%A5%E7%A8%8B%E5%88%A4%E6%96%AD.md)。

3.5/3.7的路由链为`FP32 sigmoid概率 → 加bias选Top-8 → 从原概率取权重 → 归一/缩放 → routed输出加shared输出`。bias影响选择，不应直接加入最终混合权重；改成普通softmax router可能改变语义。[路由代码](https://huggingface.co/stepfun-ai/Step-3.7-Flash/blob/main/modeling_step3p7.py#L537)

[原理] E个等规模专家、每token选k个、总批量B且路由均匀时，每专家平均批量约`Bk/E`。更稀疏的路由需要更大总批量才能保持矩阵乘效率，同时增加缓存、网络或等待压力。该近似忽略shared expert与偏斜，不是部署容量公式。

[工程分析] `T_MoE ≈ T_dispatch + max_r(T_compute,r) + T_combine`仅描述无重叠的简化关键路径。均衡最忙rank可减少拖尾，但复制/迁移专家会增加显存与通信。3.5训练中的全局bias与EP-group约束、服务侧EPLB以及请求负载调度属于不同层次。[3.5论文](https://arxiv.org/html/2602.10604v2)、[EPLB文档](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)

## 4. AFD与StepMesh：以资源分离换取更高利用率

**核心优势：** A/F独立配置显存、算力及拓扑，并汇聚多个Attention实例的FFN工作；DBO主要通过两个微批次遮蔽通信等待。分离仍增加层级交接成本，收益须按同资源同SLA验证。详见[AFD与StepMesh专题](https://github.com/wangx700/Transmission-Transfer-Station/blob/main/step%E7%B3%BB%E5%88%97%E6%8E%A8%E7%90%86%E5%92%8Cagent%E8%B0%83%E7%A0%94%E8%AF%B4%E6%98%8E/%E6%A0%B8%E5%BF%83%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/05-AFD%E4%B8%8EStepMesh%E6%9C%BA%E5%88%B6%E4%BC%98%E5%8A%BF%E5%8F%8A%E6%98%87%E8%85%BE%E5%B7%A5%E7%A8%8B%E5%88%A4%E6%96%AD.md)，其中给出接口流程、代码证据与投入建议。

```mermaid
flowchart LR
  A[Attention池与KV] --> C[激活及路由信息通信]
  C --> F[FFN聚合与专家执行]
  F --> R[结果回传]
  R --> N[下一层Attention]
```

图注：AFD概念层计算，P/D分离划分阶段，AFD划分算子资源池，EP划分专家分布，三者可组合。流水线主要利用不同批次重叠，单请求逐层依赖仍存在。

StepMesh接口可按`PushPull/ZBatchPushPull → GetBatch → FFN计算 → Respond → Wait`阅读。设备buffer注册和异步RDMA减少通信路径开销；完成通知、所有权、复用和故障恢复仍必须正确。[公开接口](https://github.com/stepfun-ai/StepMesh)

[厂商实验] Step-3在Hopper、4K上下文、FP8、无MTP、50ms TPOT限制下报告4039 tok/s/GPU，对照DeepSeek-V3为2324。它不是单请求速度，也不是Ascend结果。[实验设置](https://arxiv.org/html/2507.19427#S7)

## 5. MTP与RL：优化有效采样，而非仅生成吞吐

MTP执行`候选生成 → target验证 → 接受前缀 → 处理拒绝位置与缓存`。净收益取决于接受长度、候选/验证开销、推理长度和并发。严格与宽松接受的分布语义不同；RL中的策略概率不能直接用draft概率替代。

3.5的MIS-PO处理训练策略与rollout策略失配；版本控制限制权重过时，但不能替代数值与logprob对齐。Step5报道中的确定性算子、负载调度、MTP、量化与KV卸载是联合系统设计，不逐项认定为开源生产实现。[3.5后训练](https://arxiv.org/html/2602.10604v2)、[Step5转述](https://news.qq.com/rain/a/20260920A06EUP00)

建议同时报告原始rollout吞吐、过滤后的有效样本率、任务质量和训练稳定性。有效采样吞吐可按“满足训练准入的轨迹数/墙钟时间”统计，注明丢弃与重试规则，避免无效样本增加被误判为系统提升。

## 6. 音频生成：分阶段定位瓶颈

表注：以下为论文架构；Hz表示音频表示的帧率，不是波形采样率或模型运行速度。长度换算只用于机制解释。

| 路线 | 关键分解 | 开销与边界 |
|---|---|---|
| Audio3 Gen | 12.5Hz、16码本；主LLM预测首码本，小Transformer递推其余15个，codec出音 | 主干时间步与码本预测数不同；60秒约750帧/12000码本索引，不代表全部进入主干时间轴 |
| Audio3 Music | 50Hz单码本AR → flow-matching DiT → VAE波形 | AR、迭代渲染、解码需分测；30秒渲染块用前块末尾2秒latent衔接，局部连续性不替代全局结构 |

RVQ用逐级残差近似表示细节；Gen将时间与帧内深度分工，仍有深度串行开销。Flow Matching通过学习的速度场将噪声逐步转为条件latent；Music的渲染步骤、AR预测和音质存在权衡。不得混用两条路线的成本估计。[Gen](https://arxiv.org/html/2609.12945)、[Music](https://arxiv.org/html/2609.16034)
